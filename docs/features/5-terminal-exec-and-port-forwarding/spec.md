# Terminal, Exec, Port Forwarding, and Dashboard

- **M5-F1–F3:** Terminal is an interactive PTY in the target container. The plugin's xterm provides ordered input, output, resizing, and final state. Exec reports stdout, stderr, and exit status separately without interpreting arguments through a server shell. Both bind to the Pod UID and actual container. Bound buffering, input, and screen restoration. A log-only terminal does not create a PTY.
- **M5-F4/F5:** Forward binds the original Pod, Service, or Deployment and one explicitly resolved backend. Do not choose a Pod silently. Prefill only the first declared TCP port on the exact Service or Pod. Other ports can be added or edited; if none are declared, enter one manually. Do not issue a preliminary request or start forwarding automatically. On Service submission, resolve the backend port using `spec.ports[].port`. Use `v4.channel.k8s.io` and open one Kubernetes WebSocket per explicitly accepted local TCP connection. Report success only when the listener is ready. Show the binding, port conflicts, disconnects, and the result of an explicit stop.
- **M5-F6/F8:** Listen only on server loopback. Determine client reachability through a separate authenticated route. Dashboard must discover an actual Dashboard and start its corresponding proxy, handling absence, unreachability, and closure. Do not substitute an arbitrary existing forward or deploy Dashboard automatically.
- **M5-F7:** Bind each session to the original configuration, project, resource or backend, and owner as applicable. Permission to stop a session in the management view does not grant input or lease renewal. Reattach to the original session within its time limit. Iframe detachment does not end a task. Authorization revocation, actual target invalidation, or service shutdown invalidates old controls. Do not replay input. Stopping a local session does not guarantee reversal of remote side effects.
